# Isolated PostgreSQL CI performance experiment

This is an **opt-in engineering baseline**, not a performance optimization or production capacity result. The workflow [Isolated PostgreSQL performance baseline](../.github/workflows/performance-baseline.yml) runs on PR changes to the benchmark itself and can also be manually dispatched. It uses a fresh PostgreSQL 17.11 service container, never the operator's Docker volume or local development jobs.

## How the experiment runs

1. GitHub Actions starts a disposable PostgreSQL service in its job network, with fixed CI-only credentials.
2. `scripts/run_ci_performance.sh` checks the GitHub Actions marker, a required explicit benchmark marker, exact loopback JDBC endpoint and `public` schema before making any changes.
3. The existing `migrate.sh` applies checked migrations, and a separate Java HTTP process starts on runner loopback port 8080.
4. A readiness check must succeed before submissions. The script runs three warmup jobs, then three measurements at each of 1, 4, and 8 clients (30 distinct new jobs and 15 same-key replays per trial).
5. The order of client counts rotates across rounds to reduce systematic warmup/order bias. Each trial uses unique idempotency keys generated by the existing opt-in HTTP harness.
6. The summary program rejects missing reports, unexpected status codes, mismatched idempotency locations and workloads that differ from the protocol. The CI job publishes all JSON reports and a Markdown summary as a short-lived GitHub Actions artifact.
7. The server is terminated on exit, and the database service is disposed by GitHub Actions.

The database contains 273 accepted jobs at the end (3 warmup + 9 × 30), below the application's 1,000-job lifetime capacity. Workers are not started. No application behavior, database transactions or capacity policy is changed.

## How to interpret results

For each client count the report includes three raw trials, median observed create requests/sec, the range across trials, and the median of trial-specific create p95 response latencies.

These rates reflect one CI runner and a growing PostgreSQL job table. The concurrency settings differ in client-side scheduling, and p99 from 30 requests is particularly noisy. They **do not establish sustained capacity, CPU saturation, network behavior, worker throughput, database lock contention or production SLOs**. CI host hardware varies between runs.

Do not claim the configuration-row lock is a bottleneck solely because throughput changes with concurrency. A later experiment must collect lock-wait evidence and compare candidate transaction implementations on identical workloads and fresh databases.

## Verification and controls

- GitHub Actions runs `python3 -m unittest scripts.test_summarize_performance_ci -v` before launching the real server.
- The isolated runner refuses execution without both GitHub Actions and its dedicated marker, or if the JDBC URL/schema differ.
- The benchmark client itself only accepts loopback HTTP, disables proxies and redirects, bounds concurrency/requests, and requires explicit writes.
- Reports omit idempotency keys, payloads and job IDs. Credentials remain CI-only; server output is not uploaded.
- Failure of any trial stops the workflow. Partial JSON reports are retained by the artifact upload step for diagnosis.

**Next step after reading results:** determine whether the intake lock is the actual bottleneck using PostgreSQL wait-event sampling or measured transactional lock durations, then design any optimization as a separately reviewed experiment.
